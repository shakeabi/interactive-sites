01 — First principles

What breaks if this doesn't exist?

Before any architecture, the honest question: what is the actual failure we are engineering against? Everything downstream is a consequence of the answer.

1
DESCO runs on libraries no model has seen

deshaw.datab, deshaw.shawcache, deshaw.spyc, deshaw.djs.* — proprietary, absent from every foundation model's training data.

2
So the model doesn't fail loudly — it fails confidently

Ask about a cumulative sum on a Relation and you get a fluent, plausible, pandas-shaped answer that does not exist. The user assumes house-library knowledge, so there is no signal that anything went wrong.

3
That reframes the goal

Not "be helpful about DESCO Python." It is: never assert a deshaw.* API that wasn't verified. Refusing is an acceptable outcome; inventing is not.

4
Which forces the architecture

You need (a) domain knowledge close enough to the question to be usable, and (b) a way to check every symbol against ground truth before it reaches the user. Retrieval plus tool-verified generation — not a bigger prompt, and not a fine-tune.

The prompts say this out loud, repeatedly: "NEVER guess or invent deshaw.*/desco* code or signatures" (prompts.py:15, :73, :121). SPyC goes further — "If you have not seen a deshaw.* class... it does not exist for the purposes of your answer."
