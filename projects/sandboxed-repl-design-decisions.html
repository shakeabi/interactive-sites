Every design choice
follows from one sentence.

“An agent needs to run Python, and the second command shouldn’t re-pay for the first.” That is the whole requirement. This page derives the rest of the system from it — one question at a time, each forced by the answer before it. At every fork: the alternatives, what each one costs, and which was taken. Some of those forks are documented in tickets; others are reconstructed. The footer says which.

Because the second command throws away everything the first one earned.

An analyst agent runs import pandas; df = read_parquet(...), then asks twenty follow-up questions about df. Statelessly, each question re-pays the imports and the I/O. The work is not the computation — it is the setup, and the setup is what gets discarded.

The ticket that started this says it in one clause: “…so an agent can execute python code without paying the data loading/import costs.” Note what it does not say. It does not ask for sandboxing, images, or a notebook. Those all arrive later, as consequences.

You need more than “send string, get string.”

Write down what the channel must actually carry and the problem stops looking easy: send code; stream stdout and stderr as it happens; return structured errors with tracebacks; return images and HTML, not just text; interrupt a running statement without killing the process; and answer “are you still alive?” independently of whether you’re busy.

That is five separate concerns, and one of them — interrupt-while-busy — is the reason a single pipe cannot do the job. You need a control path that isn’t blocked behind the work.

Jupyter’s kernel protocol is exactly this, and has been for a decade: five ZeroMQ sockets (shell, iopub, stdin, control, hb), HMAC-signed messages, MIME-bundle outputs. And the server side already exists as ipykernel.

The question Jupyter deliberately leaves open: where does the process run?

An agent writes the code. Nobody reviewed it. Running it on the user’s host, as the user, with the user’s credentials and filesystem, is the default — and the default is wrong for autonomous work. But it is also exactly right for a human sitting there watching. Both are real requirements.

Then a third arrives: some work needs 20 GB and a GPU, which the dev host does not have. And a fourth: the sandbox may be a different machine entirely.

So “where” has at least four answers, and the code that uses a kernel should not have to know which. That is the seam — and jupyter_client already defines it as KernelProvisionerBase.

By lying to the client, carefully.

The remote bootstrap starts a real kernel on the far host and ships its connection dict back over SSH stdout as a single CONN:{…} line. The provisioner then forwards all five ZMQ ports to fresh local ports and rewrites the connection info — ports swapped, ip set to 127.0.0.1. The BlockingKernelClient above it cannot tell.

Two details make it hold up. SSH ControlMaster pins every subsequent operation to the same host, because the sandbox pool is one DNS name that resolves differently each lookup. And liveness is the stdin pipe: the remote blocks on a read, so SSH dropping produces EOF and a clean shutdown — no heartbeat protocol invented, none needed.

The honest cost, stated in the source itself. Forwarded ports bind 127.0.0.1, which stops remote access but not other local users. The HMAC key prevents forging messages; it does not encrypt them. A local user who connects to the iopub port reads execution output in plaintext. Filed as InfoSec#8237 and written at the top of ssh.py rather than buried.

You don’t ask the request. You ask the kernel.

The tempting check is if provisioner == "termshell". It is also wrong, and wrong in the case that matters most. When the controller is already inside a sandbox, the termshell provisioner returns None — you get a plain local kernel, because nesting isn’t supported and the kernel will inherit the existing sandbox anyway. The recorded label still says termshell.

So the label is legitimately false, and the static gate would wave it through. What actually keeps this safe is that safe_execute executes a probe inside the kernel that stats /etc/claude-code/in-sandbox and fails closed. Ground truth, from the only vantage point that can observe it.

The codebase refuses to overclaim about this. The docstring on the “safe” set reads: “Set of likely sandboxed provisioners. Downstream uses MUST still verify…”

Whoever survives long enough — and in one deployment, nobody does.

The obvious answer is the process that started it. Hold the KernelManager in memory; when the MCP server dies, the kernel dies. Simple, fast, and self-reaping.

Then Omni: Claude Code is torn down after every conversational turn while the sandbox stays warm. An in-process kernel cannot survive a single turn, and the entire value proposition — persistence — evaporates for that platform.

Hence a second model: a detached daemon that outlives its caller and watches a PID for auto-shutdown. And because a daemon nobody watches is a leak with no reaper, watch_pid is a mandatory positional argument with no default. You can pass None; you cannot forget to think about it.

Four JSON files in a 0700 directory. That’s the entire control plane.

daemon_info.json, kernel_info.json, server_info.json, daemon.log. No socket, no registry service, no database. A cold DetachedKernelSession(kernel_id=…) in a brand-new process reads those files and can find, drive, and stop a running kernel.

The clever part is that the filesystem also supplies the lock. Racing daemons resolve via O_EXCL: exactly one creates daemon_info.json, the losers check whether the winner is alive and exit 0. Liveness is (pid, create_time) — a durable process identity, not a reusable integer.

Where that discipline lapses. The daemon checks its watched parent with a bare PID and no create-time. Combine with the CLI deriving kernel_id from the grandparent PID and you get a chain: PID is reused → daemon thinks its parent lives → a new session computes the same kernel id → it attaches to the previous session’s namespace. Same user, so not a breach; deeply confusing all the same.

Interrupt the statement. Never kill the kernel.

Killing is easier and more certain. It is also self-defeating: the kernel holds the loaded dataframe, the fitted model, the open connection — the accumulated state that is the only reason this system exists. Killing to escape one bad cell throws away everything the agent built.

So a timeout sends SIGINT, synthesises a TimeoutError event, and then drains iopub until status/idle so the next call isn’t polluted by the dead cell’s tail. The kernel survives; the namespace survives.

Two sharp edges. A cell blocked in a C extension or a syscall may ignore SIGINT entirely. And with several clients on one detached kernel, the timeout clock starts at submission, not at execution — so a queued cell burns its budget waiting, and the interrupt it eventually fires is kernel-wide and can land on somebody else’s statement.

Whatever each surface decides it should — which is the point.

One display_data message may carry text/plain, text/html, image/png and application/json for the same object. The original code flattened it: text/plain became stdout, everything else became a “rich output.” So the agent received both — the same content twice, in two formats, one of them useless to it.

The fix was to stop flattening. The runtime now preserves the bundle as one typed event (StreamEvent | ErrorEvent | DisplayEvent | ClearOutputEvent) and lets each consumer project it. The ticket phrases the principle exactly: “let each surface keep its own policy for what it shows.”

So the MCP server sends the model a concise text plus an inline PNG, and suppresses text/plain when an image is already going — because the plain-text fallback of an image is worthless to a model that can see. Meanwhile a DJS chart is withheld from the agent entirely and published to the browser viewer, with a one-line note in its place. The human gets the chart; the context window doesn’t get the JSON.

Two interfaces were built, shipped simultaneously, and then measured.

An MCP server exposing six tools, and a Claude Code skill wrapping CLI scripts. Both call the same library. Both were published to the plugin marketplace. Both emit log_usage(…, {"interface": "mcp"|"cli"}) — the comparison was instrumented from the start.

MCP won on two measured grounds: it avoids re-importing the library on every call (~1 second, per invocation, forever) and it can return a PNG inline as ImageContent so the agent simply sees the plot. CLI won on three: Claude Code spills oversized Bash output to a file for free, multi-line code reads better than escaped JSON arguments, and its detached daemon survives Omni’s per-turn teardown.

The written conclusion is the right one — fold the daemon into the MCP plugin and retire the CLI. The library half shipped. The plugin half did not.

Part III · shipping it

There is no service to deploy

The library contains no listening socket — one ephemeral bind() that closes immediately, and that is all. No fleet, no endpoint, no shared state. Which means there is nobody to page, and also no central switch to flip when something is wrong.

Channel 1 · slow

The library

01git tag v<M.m.p> on genai/desco-llm
02python -m build → Artifactory pypi-genai-prod
03sleep 180s — a literal CI step, because pydeploy would otherwise race Artifactory’s own replication
04pydeploy → experimental + QA interpreters, automatically
05Production is out of band. “After next base release, these changes would move to all production hosts.” The team does not control that schedule.
Channel 2 · fast

The consumer

01/plugin marketplace add …/gai-tech-claude-plugins.git
02/plugin install desco-repl@… — a git clone into the user’s plugin cache
03.mcp.json registers a stdio server; start-mcp.sh launches the system interpreter, deliberately bypassing venvs
04Updates arrive on the next marketplace refresh — immediately
05No compatibility floor. plugin.json declares no minimum library version. The fast half can outrun the slow half, and nothing detects it until a tool call fails.

Observed skew, right now. Repo pin declares desco-llm 4.4.0; the std interpreter carries 4.6.0. The termshell provisioner mirrors an internal computation from desco_jupyter_extensions, was last repaired for version 2.37.6, and std now ships 2.37.8. That coupling is to another team’s release train — and the tests that would catch the drift are excluded from CI.

What breaks first — and it isn’t capacity

Reclamation. Three mechanisms, each partial, and the gaps line up badly with the one deployment that needs them most.

ReaperHow it worksWhere it fails
watch_pidDaemon polls the watched PID at 1 Hz and exits when it disappears Bare PID, no create-time check → PID reuse keeps it alive forever. And it is off by construction in the watch_pid=None mode Omni requires.
stale sweepRemoves kernel dirs whose daemon is dead, with an age guard against racing a concurrent start Only runs when a kernel starts. Stop starting kernels and you stop sweeping. No timer, no cron, no reaper.
explicit stop()Kills the daemon, removes metadata Requires a caller that remembers — the exact thing a torn-down per-turn process cannot do.
quotaDoes not exist. Nothing caps kernels per user, per host, or per pool. A Maestro kernel defaults to 20 GB under a 24-hour health-check window.
